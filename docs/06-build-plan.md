# 06. Build plan

How the design in docs 00 to 05 becomes a running app. Written 2026-10-21 after the five design docs were reconciled.

Working model: Fable (the main session) plans, sequences, reviews, and integrates. Opus agents build. At most five agents run at once. Every agent reads `00-decisions.md`, its assigned doc, and the repo `AGENTS.md` before writing anything, owns a disjoint set of directories, and must not touch anything outside them. Fable runs the verification gates and fixes seams between modules.

## Verification gates

Every phase ends green on all of these before the next phase starts:

```
pnpm typecheck        # tsc --noEmit, strict
pnpm lint             # eslint incl. no-restricted-imports for the (public) group
pnpm test             # vitest unit tests
pnpm build            # next build
supabase db reset     # applies every migration from zero, then seed.sql
pnpm test:sql         # SQL assertions: anon has zero table privileges and exactly two function privileges; RLS matrix per role
pnpm check:copy       # greps UI copy and docs for em and en dashes (owner rule) and fails on any hit
```

Phase 3 adds `pnpm test:e2e` (Playwright).

## Phase 0. Scaffold

One Opus agent, single writer. Reads 00, doc 02 section 1, and `../559flawless/AGENTS.md` for conventions to copy.

Deliverables:
- Next.js 16 App Router, React 19, TypeScript strict, Tailwind v4, pnpm. ESLint with `no-restricted-imports` forbidding `src/lib/supabase/server.ts` and `admin.ts` inside `src/app/(public)/**`.
- `proxy.ts` skeleton: reads `DASHBOARD_HOST` and `PUBLIC_HOST` from env, routes `(public)` vs `(dashboard)` by hostname, 404s `/api/public/*` on the dashboard host, 302s `/s/{key}` on the dashboard host to the public host, sets the two CSPs with a per-request nonce (doc 02 section 7.1). No session logic yet.
- Local dev with two hostnames: document `survey.localhost` and `s.localhost` in `.env.example` and the README; Next dev serves both.
- `components/ui/*` minimal primitive set, unstyled beyond Tailwind tokens, so module agents share one vocabulary.
- `supabase/config.toml` with pg_cron enabled, auth Google provider placeholders, storage bucket `public-assets` and the response files bucket named in doc 01.
- `scripts/check-copy.sh`, package scripts for every gate, `.env.example` listing every variable the docs mention (Supabase URL and keys, hosts, Turnstile site and secret keys, `CRON_SECRET`).
- `AGENTS.md` first draft: stack, the two-hostname rule, the "anon has two functions" rule, where authorization lives, the no em dash rule, how to run gates.

Gate: all gates pass on an empty app. Fable reviews `proxy.ts` line by line.

## Phase 1. Foundation

Two waves. Everything here is frozen after the phase; later changes go through Fable.

### Wave 1, two agents in parallel

**1A SQL foundation.** Reads doc 01 in full, doc 02 sections 4 and 5 for the public function contracts, doc 03 section 2 for the definition JSON that `publish_survey_version` must validate. Writes `supabase/migrations/0001` to `0017` exactly as doc 01 section 15 lists them, `seed.sql`, and `supabase/tests/*.sql`. Tests must cover: anon privilege assertion; `is_member` role ordering; a published version refusing updates; `submit_response` enforcing `response_cap`, token single use, and `visible_keys`; `resolve_public_survey` returning nothing for an unknown key; `effective_limits` merging overrides; workspace lifecycle timing guards. Gate: `supabase db reset` and `pnpm test:sql` green.

**1B TypeScript core.** Reads doc 03 sections 2 to 4 and 00. Writes `src/lib/survey/*` with no React and no Supabase imports: definition types with `schema_version`, `migrate.ts`, the logic engine (conditions, show/hide, skip, end-survey, piping, calculated fields, scoring, randomization with seed), `validateSubmission` with modes `page`, `partial`, `final`, `splitDefinition` and the server-only key list, and the publish lint rules. Vitest fixtures: at least one definition per question type, one branching survey, one quiz. Gate: `pnpm test` green with coverage on the engine above 90 percent.

### Wave 2, two agents in parallel

**1C Renderer.** Depends on 1B. Reads doc 03 sections 1, 5, 8 and doc 02 section 11. Writes `src/components/survey/renderer/*`: the type registry with an `Input` component for every v1 type in doc 03's table, `SurveyShell`, `PageView`, `QuestionFrame`, `useSurveyState`, `useAutosave` (callback based, no network), `ThemeProvider` writing CSS variables, keyboard and screen reader behavior per type. Props are the public definition plus callbacks; nothing in here knows about Supabase, pixels, or Turnstile. Testing-library smoke tests per type. Gate: typecheck, tests, and a Storybook-free `/dev/renderer` page (dashboard group, dev only) that renders every fixture.

**1D Data access and auth plumbing.** Depends on 1A. Runs `supabase gen types` into `src/types/database.ts`. Writes `src/lib/supabase/{server,browser,anon,admin}.ts` with the origin rules from doc 02 section 1 (cookies host-only to the dashboard host, anon client with no cookie adapter). Writes `src/lib/db/*`: one typed wrapper per RPC in doc 01 section 12 with zod input validation and a discriminated error type that maps SQL exception codes (`plan_limit:*` is gone; map `survey.*`, `limit.*`, `lock.*`, `auth.*` prefixes). Adds `requireUser`, `requireMember(workspaceSlug, minRole)`, `requirePlatformAdmin` server helpers and the session refresh branch in `proxy.ts` for the dashboard host only. Gate: typecheck, unit tests on error mapping, and an integration test against local Supabase that calls each wrapper once as each role.

Freeze: Fable tags the commit `foundation-frozen` and updates `AGENTS.md` with the module ownership table above.

## Phase 3. Integration and hardening

Fable plus two agents.

**3A End-to-end tests.** Playwright against local Supabase and the dev server on both hostnames, Turnstile test keys. Flows: platform admin creates workspace and invite; invitee signs in with the invite link; editor builds a branching survey with an identity question and a file upload, publishes, opens it; anonymous respondent submits on the public host with a hidden `?src=` field; inbox shows it live; contact is created; respondent submits a second survey via a personalized token and the timeline shows both; viewer opens analytics and a shared report link; editor exports CSV; admin erases the respondent and the export no longer contains them. Use the `webapp-testing` skill.

**3B Security and accessibility audit.** Re-run the anon privilege assertion against the deployed schema; RLS matrix test per role across every table; CSP headers on both hosts; cookie attributes (host-only, Secure, SameSite); confirm pixels never render on the dashboard host or in preview; axe on the public page for every question type; Lighthouse performance budget from doc 02 section 11; a review of every `SECURITY DEFINER` function for search_path and input checks.

Fable: fix findings, finalize `AGENTS.md`, write the deployment runbook below into the README.

## Phase 4. Deploy

Checklist, run by the owner with Fable:
1. Supabase project (pick region, record it in 00). Enable pg_cron. Push migrations. Run seed with the real platform admin email.
2. Google OAuth client with redirect to the dashboard host callback. Configure in Supabase Auth. Leave email confirmations off for OAuth; keep password auth enabled but document the admin-minted reset flow.
3. Vercel project with both hostnames attached, env vars from `.env.example`, `vercel.json` cron entries for orphan sweep (hourly), retention (daily 03:00 UTC), workspace purge (daily).
4. Turnstile widget for the public host; keys into Vercel env.
5. Platform admin writes the privacy notice in `/admin` before any survey is opened.
6. Smoke test the Phase 3 e2e flow against production with a throwaway workspace, then archive and purge it to prove the lifecycle.

## Agent brief template

Every Phase 1 to 3 brief contains, in this order: the goal in two sentences; the files to read (00, the doc sections, `AGENTS.md`); the directories owned and the explicit list of what must not be touched; the gate commands that must pass; the reminder that authorization lives in RLS and route guards are UX; the no em or en dash rule; and the report format (under 250 words: what was built, deviations from the doc with reasons, open questions, files created outside the owned set).

## Open questions for the owner, consolidated

Defaults in parentheses are what the build assumes until the owner says otherwise.

Blocking before public surveys open:
1. Second hostname for public pages, ruling R15 (yes). If no, `custom_script` and `gtm` pixel types are removed.
2. Who writes and signs off the organization privacy notice (owner; a platform admin edits it in `/admin`).
3. Who else is a platform admin (owner only until named; two is safer).

Product behavior:
4. Default `pixel_consent_mode` (banner).
5. Partial response lifetime (30 days, then purged, separate from complete-response retention).
6. Restrict workspace invite links to the organization email domain (off; add as a setting later).
7. Admin-assisted password reset long term (yes for v1; revisit an auth-only SMTP sender later).
8. Workspace owners see abuse reports on their own surveys (yes, read only).
9. Seven day archive period before a workspace delete (yes; platform admin may skip it).
10. Viewers can open the builder preview (yes, read only).
11. Quiz mode shows correct answers to respondents (score only by default, per-survey toggle).
12. Signature questions: drawn PNG plus timestamp only, no IP (yes; an e-sign audit trail is out of scope).
13. Shared reports: minimum cell size 3 fixed (yes), verbatim quotes (off).
14. Meta Pixel completion event name (Lead, configurable later).
15. Platform admin upload override ceiling (100 MB).
16. Surveys default to `noindex` (yes).

Deferred to v2 unless a department is blocked: multi-language surveys, iframe embeds, department template packs, custom lead statuses, PDF report export, respondent self-service data export.
